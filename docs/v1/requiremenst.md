# Requirements Document

## Introduction

CommunitAI is an AI-powered Chief of Staff platform for community leaders, built on DigitalOcean Gradient AI. It eliminates the administrative burden of community management by automating meeting transcription, action item extraction, sentiment analysis, and report generation — so community leads can focus on people, not paperwork.

The platform supports in-browser meeting recording, audio file uploads, and a dashboard for tracking tasks, past meetings, and shareable reports.

Architecture overview:
- **Transcription**: OpenAI Whisper API (speech-to-text)
- **AI Processing**: DigitalOcean Gradient AI Serverless Inference via OpenAI-compatible `/v1/chat/completions` endpoint (e.g., `meta-llama-3.1-70b-instruct` or `anthropic-claude-haiku-4.5`)
- **Agent Orchestration**: CommunitAI Agent built with DigitalOcean Gradient AI Agent Development Kit (ADK)
- **Storage**: DigitalOcean Spaces for audio files and generated reports; PostgreSQL (DigitalOcean Managed DB) for metadata
- **Backend**: Python FastAPI using the Gradient ADK and Spaces SDK
- **Frontend**: Next.js + Tailwind CSS

## Glossary

- **CommunitAI**: The full-stack AI platform being built.
- **Recorder**: The in-browser audio recording component.
- **Uploader**: The audio file upload component.
- **Transcriber**: The service that converts audio to text by calling the OpenAI Whisper API.
- **Transcript**: The text output produced by the Transcriber from a meeting audio file.
- **Extractor**: The AI service that identifies action items from a Transcript via Gradient AI Serverless Inference.
- **Action_Item**: A discrete task with an assignee and optional due date, extracted from a Transcript.
- **Sentiment_Analyzer**: The AI service that detects community health signals from a Transcript via Gradient AI Serverless Inference.
- **Sentiment_Report**: The structured output of the Sentiment_Analyzer, including detected signals such as burnout, conflict, or positive momentum.
- **Summarizer**: The AI service that generates a TL;DR summary from a Transcript via Gradient AI Serverless Inference.
- **Summary**: A concise, shareable text report generated by the Summarizer.
- **CommunitAI_Agent**: The Gradient AI Agent built with the ADK that orchestrates all AI processing tasks (transcription dispatch, extraction, sentiment analysis, summarization).
- **ADK**: The DigitalOcean Gradient AI Agent Development Kit — a Python SDK used to deploy the CommunitAI_Agent as a hosted, production-ready service.
- **Gradient_Inference**: The DigitalOcean Gradient AI Serverless Inference endpoint (`https://inference.do-ai.run/v1/chat/completions`) used for LLM-based AI tasks.
- **Whisper_API**: The OpenAI Whisper API used exclusively for speech-to-text transcription.
- **Dashboard**: The main UI view where community leads manage meetings, tasks, and reports.
- **Meeting**: A recorded or uploaded audio session with associated Transcript, Action_Items, Sentiment_Report, and Summary.
- **Storage**: DigitalOcean Spaces (S3-compatible) used to persist audio files and generated reports.
- **Database**: DigitalOcean Managed PostgreSQL database used to persist Meeting metadata, Action_Items, and processing statuses.

## Requirements

### Requirement 1: In-App Meeting Recording

**User Story:** As a community lead, I want to record meetings directly in the browser, so that I can capture discussions without switching to an external tool.

#### Acceptance Criteria

1. THE Recorder SHALL provide a start, pause, and stop recording control in the browser UI.
2. WHEN the user starts a recording, THE Recorder SHALL capture audio from the user's microphone using the browser MediaRecorder API.
3. WHEN the user stops a recording, THE Recorder SHALL save the audio file to the user's local machine in a widely-supported format (MP3 or WAV).
4. WHEN the user stops a recording, THE Recorder SHALL make the audio file available for upload to Storage or direct processing.
5. IF the browser does not support the MediaRecorder API, THEN THE Recorder SHALL display an error message informing the user to use a supported browser.
6. IF microphone permission is denied by the user, THEN THE Recorder SHALL display an error message explaining that microphone access is required.
7. WHILE a recording is in progress, THE Recorder SHALL display a visible recording indicator and elapsed time to the user.

---

### Requirement 2: Audio File Upload

**User Story:** As a community lead, I want to upload existing audio recordings, so that I can process meetings that were recorded outside the app.

#### Acceptance Criteria

1. THE Uploader SHALL accept audio files in MP3, WAV, and M4A formats.
2. WHEN a valid audio file is selected, THE Uploader SHALL upload the file to Storage and associate it with a new Meeting record.
3. IF a file exceeding 500MB is selected, THEN THE Uploader SHALL reject the file and display a message stating the maximum file size.
4. IF a file with an unsupported format is selected, THEN THE Uploader SHALL reject the file and display a message listing the accepted formats.
5. WHILE an upload is in progress, THE Uploader SHALL display an upload progress indicator to the user.

---

### Requirement 3: Meeting Transcription

**User Story:** As a community lead, I want meeting audio converted to text automatically, so that I have a searchable record of what was discussed.

#### Acceptance Criteria

1. WHEN a Meeting audio file is available in Storage, THE Transcriber SHALL send the audio to the Whisper_API and produce a Transcript.
2. THE Transcriber SHALL associate the resulting Transcript with its source Meeting record.
3. WHEN transcription is complete, THE Transcriber SHALL store the Transcript in Storage and update the Meeting status to "transcribed".
4. IF the Transcriber receives an error response from the Whisper_API, THEN THE Transcriber SHALL retry the request up to 3 times before marking the Meeting status as "transcription_failed".
5. WHILE transcription is in progress, THE Dashboard SHALL display the Meeting status as "processing" to the user.
6. THE Transcriber SHALL produce a Transcript that preserves speaker turns where the Whisper_API supports speaker diarization.

---

### Requirement 4: Action Item Extraction

**User Story:** As a community lead, I want action items automatically identified from meeting transcripts, so that I don't have to manually review notes to find follow-ups.

#### Acceptance Criteria

1. WHEN a Transcript is available for a Meeting, THE Extractor SHALL send the Transcript to Gradient_Inference and extract a list of Action_Items.
2. THE Extractor SHALL identify each Action_Item with at minimum: a description of the task and the name of the assignee mentioned in the Transcript.
3. WHERE a due date is mentioned in the Transcript, THE Extractor SHALL include the due date in the Action_Item.
4. WHEN extraction is complete, THE Extractor SHALL persist the Action_Items in the Database and associate them with the source Meeting.
5. IF Gradient_Inference returns no Action_Items for a Transcript, THEN THE Extractor SHALL record an empty list and mark extraction as complete rather than treating it as an error.
6. THE Dashboard SHALL display all pending Action_Items grouped by Meeting, showing description, assignee, and due date where available.

---

### Requirement 5: Sentiment Analysis

**User Story:** As a community lead, I want to detect burnout, conflict, or community health signals in meeting transcripts, so that I can proactively address issues before they escalate.

#### Acceptance Criteria

1. WHEN a Transcript is available for a Meeting, THE Sentiment_Analyzer SHALL send the Transcript to Gradient_Inference and produce a Sentiment_Report.
2. THE Sentiment_Report SHALL include at minimum: an overall sentiment classification (positive, neutral, negative) and a list of detected signals (e.g., burnout, conflict, disengagement, positive momentum).
3. WHERE a detected signal has supporting evidence in the Transcript, THE Sentiment_Analyzer SHALL include a brief excerpt or rationale in the Sentiment_Report.
4. WHEN analysis is complete, THE Sentiment_Analyzer SHALL persist the Sentiment_Report in the Database and associate it with the source Meeting.
5. IF Gradient_Inference returns an error during sentiment analysis, THEN THE Sentiment_Analyzer SHALL retry the request up to 3 times before marking the Sentiment_Report status as "analysis_failed".
6. THE Dashboard SHALL display the Sentiment_Report for each Meeting, highlighting any negative signals with a visual indicator.

---

### Requirement 6: Automated Meeting Summaries

**User Story:** As a community lead, I want a TL;DR summary generated from each meeting, so that I can share key outcomes with my community on Discord or Slack without writing notes manually.

#### Acceptance Criteria

1. WHEN a Transcript is available for a Meeting, THE Summarizer SHALL send the Transcript to Gradient_Inference and produce a Summary.
2. THE Summary SHALL include: key discussion points, decisions made, and a list of Action_Items in plain text.
3. THE Summary SHALL be formatted so that it can be copied and pasted directly into Discord or Slack without additional editing.
4. WHEN the Summary is generated, THE Summarizer SHALL persist the Summary in Storage and associate it with the source Meeting.
5. THE Dashboard SHALL provide a "Copy to Clipboard" control for each Summary.
6. IF Gradient_Inference returns an error during summarization, THEN THE Summarizer SHALL retry the request up to 3 times before marking the Summary status as "summarization_failed".

---

### Requirement 7: CommunitAI Agent Orchestration

**User Story:** As a developer, I want all AI processing tasks orchestrated by a single Gradient AI Agent, so that the system has a unified, maintainable entry point for all AI workflows.

#### Acceptance Criteria

1. THE CommunitAI_Agent SHALL be implemented using the ADK and deployed as a hosted service on the DigitalOcean Gradient AI platform.
2. WHEN a Meeting audio file is ready for processing, THE CommunitAI_Agent SHALL orchestrate the sequential execution of transcription dispatch, action item extraction, sentiment analysis, and summarization.
3. THE CommunitAI_Agent SHALL call Gradient_Inference using the OpenAI-compatible `/v1/chat/completions` endpoint for all LLM-based tasks (extraction, sentiment analysis, summarization).
4. THE CommunitAI_Agent SHALL call the Whisper_API for transcription tasks and SHALL NOT use Gradient_Inference for speech-to-text.
5. WHEN a processing step fails after all retries are exhausted, THE CommunitAI_Agent SHALL update the Meeting status in the Database to reflect the failed step and halt further processing for that Meeting.
6. THE CommunitAI_Agent SHALL expose an entrypoint decorated with the ADK `@entrypoint` pattern so that it can be invoked by the FastAPI backend.
7. WHERE a Gradient AI Knowledge Base containing community management best practices is attached to the CommunitAI_Agent, THE CommunitAI_Agent SHALL use it to improve the quality of extracted Action_Items, Sentiment_Reports, and Summaries.

---

### Requirement 8: Community Lead Dashboard

**User Story:** As a community lead, I want a single dashboard view of all my meetings, tasks, and reports, so that I can manage my community's administrative work in one place.

#### Acceptance Criteria

1. THE Dashboard SHALL display a list of all Meetings, ordered by date descending, showing title, date, and processing status.
2. THE Dashboard SHALL display a list of all pending Action_Items across all Meetings, showing description, assignee, due date, and source Meeting.
3. WHEN a community lead selects a Meeting, THE Dashboard SHALL display the Transcript, Sentiment_Report, Summary, and Action_Items for that Meeting.
4. THE Dashboard SHALL allow a community lead to mark an Action_Item as complete, updating its status in the Database.
5. WHEN an Action_Item is marked complete, THE Dashboard SHALL remove it from the pending Action_Items list.
6. THE Dashboard SHALL display the overall Sentiment_Report classification for each Meeting in the Meeting list using a color-coded indicator (green for positive, yellow for neutral, red for negative).
7. IF a Meeting has a status of "transcription_failed", "analysis_failed", or "summarization_failed", THEN THE Dashboard SHALL display the failure status and provide a retry control for the failed step.

---

### Requirement 9: Storage and Persistence

**User Story:** As a community lead, I want my meeting recordings, transcripts, and reports stored reliably, so that I can access past meetings at any time.

#### Acceptance Criteria

1. THE Storage SHALL persist all audio files uploaded or recorded by the user in DigitalOcean Spaces.
2. THE Storage SHALL persist all Transcripts, Summaries, and Sentiment_Reports as files in DigitalOcean Spaces.
3. THE Database SHALL persist all Meeting metadata, Action_Items, and processing statuses in PostgreSQL.
4. WHEN a Meeting is deleted by the user, THE Storage SHALL delete the associated audio file, Transcript, Summary, and Sentiment_Report files, and THE Database SHALL delete the associated Meeting record, Action_Items, and status entries.
5. THE Storage SHALL enforce access controls so that a user can only retrieve Meeting data associated with their own account.
6. IF a Storage write operation fails, THEN THE CommunitAI backend SHALL return an error response to the client and log the failure with sufficient detail for diagnosis.
7. IF a Database write operation fails, THEN THE CommunitAI backend SHALL return an error response to the client and log the failure with sufficient detail for diagnosis.
